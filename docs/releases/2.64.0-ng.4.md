# filebrowser-ng 2.64.0-ng.4 — prepared release notes

Status: **local candidate, not published**, prepared on 2026-10-29. The current published version remains [2.64.0-ng.3](https://github.com/dawidpiotrowski/filebrowser-ng/releases/tag/v2.64.0-ng.3). There is no ng.4 registry digest yet. The local verification record is [ng.4 readiness](../security/release-readiness-2026-10-29.md).

This release combines the file-integrity repairs and browser-session migration developed after ng.3. It changes authentication for custom clients and the filesystem permissions needed for overwrites. Review the [upgrade steps](../migration.md#upgrade-from-2640-ng3-to-2640-ng4-prepared) before switching an existing installation.

## Security and file integrity

- Browser authentication uses opaque HttpOnly, host-only cookies with SameSite=Strict, Secure on TLS and trusted HTTPS proxies, two-hour default idle expiry and a 24-hour absolute cap. No login bearer remains in browser storage or download URLs. Login/signup and unsafe cookie requests require CSRF proof and origin checks.
- Tabs coordinate login, stable renewal and logout, including a storage/focus fallback. Delayed failures cannot revoke a later login; account changes reload private client state and block queued writes/uploads if reload is cancelled.
- TUS transfers belong to their creator and original target identity. Chunks remain private until complete; cancellation/expiry preserves visible files. New public links contain 128 bits of randomness; existing links remain usable. Invalid/overflowing share lifetimes return client errors.
- Native no-replace rename closes the conflict race. Uploads, editor saves and copies publish complete staged files, preserve required security metadata, propagate write/flush/close errors and reject competing changes. ETag conditions reject stale editor saves with 412 and retain unsaved text.
- The x/net update to v0.62.0 removes the new package advisories [GO-2026-6860](https://pkg.go.dev/vuln/GO-2026-6860) and [GO-2026-6866](https://pkg.go.dev/vuln/GO-2026-6866). The pre-update call-graph scan did not identify calls to the affected functions; this is dependency maintenance, not a claim of a demonstrated exploit in filebrowser-ng.

## Compatibility and operator action

Everyone signs in again. Browser login/renewal now return JSON session state. Machine credential login requires `X-FB-Client: api`, no cookies/browser metadata, and returns an API-audience JWT for X-Auth; renewal still consumes the previous JWT. Custom browser clients must use the cookie-bound CSRF protocol.

TLS-terminating proxies must have their actual TCP peer CIDRs configured in `trustedProxies`, preserve external Host and overwrite X-Forwarded-Proto. Proxy identity authentication still needs its separate identity allowlist/header on every request. Do not infer trust from forwarded visitor addresses.

Container ports, UID/GID overrides and data/database mounts remain compatible. Existing accounts, password hashes, preferences, scopes and shares are retained; session records gain fields/indexes. Atomic replacement needs directory write/delete permission and temporary space, and creates a new inode. Open readers/hardlinks keep old contents. The staging prefix `.filebrowser-ng-staging-` is reserved. Pending uploads must restart after service restart. Cross-volume directory moves return 501; directory copies are per-file transactions.

Keep one writer process per tree. Atomic visibility does not promise a filesystem-wide transaction, uninterrupted upload resumption, fencing against arbitrary host writers, or power-loss durability for every NAS/storage stack. Browser HttpOnly does not replace script CSP; CSP, session inventory/scoped machine credentials and MFA remain on the roadmap.

## Distribution and publication

Planned container: `ghcr.io/dawidpiotrowski/filebrowser-ng:2.64.0-ng.4`, Linux amd64/arm64, unprivileged scratch runtime. This name is prospective until the publish workflow succeeds. Existing Compose defaults stay on ng.3 during preparation. No NAS deployment is part of publication.

The publish workflow must verify the exact tagged source, with Linux/macOS/Windows tests, browser behavior and non-root container upgrade/restart tests on both architectures, before pushing the numbered, commit and latest tags. After publication, record the resulting immutable digest and verify anonymous pulls for both platforms. Retain SBOM/provenance attestations, including their OCI metadata entries.

A proposed release is not a green CI result: native Windows, native amd64 runners and the actual Ugreen proxy/filesystem checks must be distinguished from local cross-compilation/emulation. See the readiness record for the evidence available and remaining gates.
