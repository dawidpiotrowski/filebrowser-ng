# Migration

## Upgrade from 2.64.0-ng.3 to 2.64.0-ng.4 (prepared)

ng.4 is prepared locally and is not published. Keep using the published ng.3 image until publication is explicitly confirmed. The [prepared release notes](releases/2.64.0-ng.4.md) describe the candidate and its remaining publication gates.

1. Stop the service and take a consistent database/configuration backup and data snapshot. Keep backups outside the served tree. Test on copies and retain the ng.3 image/digest for recovery. Run one writer process per database/tree.
2. For HTTPS terminated at a proxy, configure the new top-level `trustedProxies` server option with the proxy's **actual TCP peer CIDRs**. Preserve the external Host and overwrite X-Forwarded-Proto with `https`. The proxy-auth identity allowlist also supplies scheme trust in proxy-auth mode. Do not trust an entire LAN or a visitor-supplied forwarded address to avoid identifying the proxy. JSON authentication also needs this scheme trust; otherwise HTTPS-origin writes can fail. Direct TLS and plain LAN HTTP keep their distinct cookie settings. See [authentication](authentication.md#https-proxies-and-lan-http).
3. Preserve UID/GID, `/srv`, `/database/filebrowser.db`, the 8080 container port and existing mounts. ng.4 extends persisted session records/indexes; it does not require a new database or account recreation. All existing JWT sessions require a fresh login, and the browser removes legacy JWT storage automatically.
4. Update machine clients: send `X-FB-Client: api` only for credential login, without cookies or browser metadata; retain the returned JWT for X-Auth. Browser login/renewal return JSON and use cookie-bound CSRF headers instead of JWTs. Machine renewal still consumes its old token. Custom browser clients must adopt the complete cookie/CSRF protocol.
5. Check directory write/delete rights, temporary space and preservation of existing ownership/ACL/xattrs on a copied representative directory. Atomic replacement creates a new inode; open readers and hardlinks retain the previous inode. Unsupported filesystems or unpreservable security metadata fail without a truncating fallback. Cross-volume directory moves return 501.
6. Inventory legitimate names beginning with `.filebrowser-ng-staging-` in any path component; this namespace is now reserved. New TUS uploads remain private until completion. Pending uploads cannot resume across upgrade/restart; start them again. New links have longer opaque IDs, while existing public links retain their permissions and expiry.
7. Once a numbered image is published, test a replacement container against the copies. Verify login in two tabs, logout, file upload/download, overwrite/editor conflicts, TUS, proxy identity, shares and restart persistence. Only then repeat the backup and replace the live container. This preparation does not deploy anything.

If recovery is necessary, stop ng.4 before restoring the **matching cold database/configuration and data snapshot** with ng.3. Do not run both against one tree or assume a binary downgrade rolls back new file contents. ng.3 lacks the fixes described here; recovery is an operational fallback, not a security remediation.

## Migration from upstream File Browser v2.63.23

1. Stop the upstream process. Back up its database, configuration, and data. Keep the backup outside the served tree.
2. Pull the fork image (see [Docker and NAS](docker.md)) or build filebrowser-ng and point it at the same database and root. The database schema retains upstream users, permissions, settings, and shares, and adds a session bucket. Test with a copied database and data first.
3. If the old instance used hook authentication, switch it to JSON or proxy authentication using the CLI before starting the new server. Command execution and hooks no longer run; remove `--disable-exec=false`.
4. For proxy authentication, configure `--auth.trustedProxies` with the actual proxy peer CIDRs. Restrict backend access to that proxy and overwrite identity headers. Use TLS; configure `X-Forwarded-Proto` correctly so cookies are marked Secure behind TLS termination.
5. Remove the Redis upload-cache URL and run one writer process per tree. Redis did not fence concurrent filesystem writes. Expired incomplete uploads remain on disk rather than risking deletion of a subsequently replaced file; clean abandoned files during a maintenance window.
6. If signup is enabled, enable `createUserDir`. Self-registration into a shared default/root scope is rejected. Verify existing users' scopes; migration cannot infer which historical accounts were provisioned unsafely.
7. All users must sign in again. Browser credentials move to HttpOnly cookies; startup removes legacy `jwt` entries from localStorage/sessionStorage. Configure `trustedProxies` for a TLS-terminating reverse proxy, preserving Host and overwriting X-Forwarded-Proto. See [authentication and API migration](authentication.md). Machine login now explicitly requires `X-FB-Client: api`, with no cookies/browser metadata. Old JWTs lack the API audience/kind and are rejected; machine renewal still consumes the old token and requires retaining its replacement.
8. Old password-share download URLs containing `?token=` no longer bypass the password. Recipients use the ordinary share page and enter its password; subsequent downloads use an HttpOnly cookie valid for at most 15 minutes. Test media playback, EPUBs, CSVs, and browser integrations before rollout.

Subtitle conversion is capped at 2 MiB; VTT streams directly. Text previews are capped at 10 MiB even if a file grows after stat. Archive trees are capped at 100,000 entries and 128 levels, and skip special files and cyclic directory aliases.

The new container is published to GHCR, contains no shell, runs as UID/GID 65532, and listens on 8080. Match `user:` to your existing NAS UID/GID rather than changing ownership of an entire data tree. The supplied Compose file binds to loopback; [compose.nas.yaml](../compose.nas.yaml) makes paths, ownership, and the bind address explicit. The upstream S6 image and upstream install scripts are not fork distribution channels.

After a successful test migration, take a fresh backup and switch the deployment. Rolling back to upstream reintroduces its known vulnerabilities; do not treat rollback as a security fix.

## Changes in 2.64.0-ng.3

- Complete user replacements (`which` missing/null/empty or `all`) and changes to passwords, identities, permissions, scope, password locks, commands and rules require the current password under JSON authentication. Preference-only updates still work without it. API clients must send editable field names; ID/runtime filesystem fields and unknown fields are rejected before any writes.
- The last administrator cannot be deleted or demoted through API/CLI, including concurrent operations. Invalid regex rules are rejected before saving. Existing malformed rules deny file access; fix global rules in settings or repair user rules through an administrator.
- Failed rename operations fall back to copy/delete only for cross-device moves. Other filesystem errors are returned instead of being bypassed. Failed copies retain the source/partial destination for recovery and never unconditionally delete an existing destination. Interrupted overwrite atomicity remains planned work.
- Application pages now restrict embedding to the same origin and set no-referrer, navigation and browser-permission headers. Same-origin PDF previews remain allowed. Integrations embedding the UI on another origin need an explicit policy design. HSTS remains a reverse-proxy/TLS endpoint setting.
- Thumbnail cache identity now includes finer timestamps and size. Existing cache entries are ignored, not migrated; caches may be cleared separately during maintenance. The database schema and UID/GID/container paths do not change.

See the [review](security/code-review-2026-10-21.md) for evidence and remaining boundaries, and the [roadmap](security/roadmap.md) for upcoming security features.

## Unreleased local changes

These changes follow `v2.64.0-ng.3` and form the prepared ng.4 candidate. They are not yet available in a published image. UID/GID and container paths remain the same; persisted session records and HTTPS proxy/client configuration change as described above.

- Copy requests without `override=true` return 409 if another operation creates a destination file before its writable open, including inside recursive copies. Modify permission alone does not opt into overwriting. Copying a file onto itself through a hardlink/symlink returns an error and preserves source contents. A failed Sync/Close during a cross-volume move retains the source; partial destination data may remain for recovery. Atomic rename and overwrite are still planned work.
- TUS HEAD/PATCH/DELETE require the upload creator's account, in addition to existing permissions. A different account cannot take over an upload merely because it shares the directory; use a new upload or the ordinary permitted file operations. A replacement filesystem object at the same path causes 409. The creator can resume after session renewal. Adapters whose root lacks stable filesystem identity reject TUS creation with 501 before mutation; use regular uploads with such adapters. The created handle must also supply stable identity. OS-backed deployments retain TUS. Cache expiry and server restart still lose resumability and retain incomplete files on disk.
- New share IDs are 22 URL-safe characters; clients must treat hashes as opaque strings of variable length. Existing short links continue to work. Explicit expiry must be positive, use seconds/minutes/hours/days (omitted unit means hours), and fit a Go duration. Invalid/overflowing values return 400 instead of being accepted or returning 500. Omitted expiry remains permanent. Passwords longer than bcrypt's 72-byte limit return 400.
- Browser login/renewal return JSON session state, never a JWT. Unsafe writes and TUS chunks require cookie-bound CSRF headers. Browser renewals are idempotent with a stable cookie; tabs coordinate through Web Locks and change notifications, with a storage/focus fallback. Session/account changes reload the page and block pending writes under a different session. [Protocol and verification](security/browser-sessions-2026-10-29.md).

See the [local review](security/follow-up-review-2026-10-21.md) for evidence and limitations.

## Atomic file mutations (local, unreleased)

This subsequent local patch implements the rename/overwrite work described above. It has no published image or deployment change.

- Rename without explicit override, including an automatically suffixed destination, now uses native atomic exclusion. A competing destination returns 409 and retains the source; retry suffix selection if needed. Existing case aliases may conflict according to native filesystem behavior. Unknown adapters/filesystems cannot silently fall back to unsafe rename.
- Ordinary uploads, editor saves, copies and cross-volume regular-file moves stage complete content before publishing it. Failed body reads, observed cancellation, disk-full and file Sync/Close errors before commit preserve the previous target. Existing readers/hardlinks retain the old inode. Replacing a file requires directory write/delete rights, enough temporary disk space and permission to preserve its security metadata. Supported mode/ownership/xattr/ACL preservation failures abort the replacement.
- Resource GET returns an opaque ETag, and `If-Match` is supported for writes and TUS creation. The bundled editor sends the loaded version automatically. A stale save returns 412 and retains the editor's unsaved content. Treat tags as opaque; do not reconstruct them from modification time and size. Clients omitting the header remain compatible, but do not gain stale-editor detection before a write begins.
- TUS destinations no longer appear empty/partial during creation or transfer. The old file remains readable during an overwrite; a new file appears after the final chunk commits. HEAD reports private staged progress. Cancellation or three-minute idle expiry discards only private chunks; it never removes the old visible file. Graceful shutdown discards pending stages. A server restart requires a new upload.
- `.filebrowser-ng-staging-` components are reserved, case-insensitively, including through aliases and configured share/branding roots. Inventory pre-existing files/directories using that prefix before a later upgrade; move legitimate data to an ordinary name. Crash leftovers remain inaccessible through the app. Recover or remove them deliberately during maintenance; do not blindly delete matching paths while writes are active.
- The process allows at most 256 active staged writes/TUS jobs and returns 429 when full. This does not replace disk quotas or a per-user budget. Run one writer process per tree.
- Same-volume file/directory moves remain native renames. Cross-volume **directory** moves now return 501 rather than attempting a non-transactional copy/delete. Directory copying is still a sequence of atomic file commits and may be partial on failure. Directory copies into symlink-aliased descendants are rejected before destination creation.
- After the atomic rename has committed, lost responses or a directory-sync failure can still mean the complete new file is present. Re-read before retrying. Windows directory durability differs from Unix, and native Windows/NAS validation remains required before a later publication.

See the [implementation review](security/atomic-writes-2026-10-21.md) for exact guarantees, tests and remaining limits. Database schema and container configuration remain unchanged.
