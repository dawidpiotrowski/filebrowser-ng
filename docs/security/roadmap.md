# Security roadmap

Updated after the [local follow-up review](follow-up-review-2026-10-21.md), starting from `v2.64.0-ng.3`. **Current work is committed locally only: no push, tag, release, image publication or deployment.** Features below are planned unless a completed local slice is explicitly identified. The published [earlier review](code-review-2026-10-21.md) remains historical evidence for ng.3.

The next implementation order is **file integrity (P0.2), browser sessions (P0.1), then application CSP (P0.3)**. These identifiers are retained from the earlier plan. File integrity comes first because the review reproduced permission races and data loss; MFA follows a sound session lifecycle. Independent bounded fixes need not wait for an entire milestone.

## Threat model and current status

Protect private files, account/session credentials and share grants against anonymous callers, malicious files/paths, an authenticated account exceeding its Create/Modify/Delete/Download/Share permissions, and concurrent operations in overlapping user scopes. Treat a stolen administrator session as a reason to require recent reauthentication for sensitive changes. Test network interruption, disk-full and filesystem errors as integrity failures. Host administrators and arbitrary host-side writers require OS ownership/quotas and operational controls; an application mutex cannot fence them. Keep one writer process per tree until a real fencing protocol exists.

| --- | --- | --- |
| P0.2 copy completion | Exclusive non-override file creation, opened-handle alias checks, propagation of Sync/Close failures. NG-14–16. | Native no-replace rename, transactional/conditional overwrites, private staging and directory recovery. |

## Milestones

| Order | Feature and implementation scope | Acceptance criteria |
| --- | --- | --- |
| P0.1 | **Browser sessions without JavaScript-readable tokens.** Use an HttpOnly cookie for browser authentication, a user/bootstrap endpoint, origin/CSRF checks for unsafe methods, absolute plus idle expiry, and a multi-tab renewal/logout protocol. Keep machine API credentials separate. | No reusable login token in localStorage, sessionStorage, URLs or JavaScript response bodies. Cross-site login/logout/write requests rejected. Two tabs can renew simultaneously and logout invalidates both. Password changes and database restart preserve the intended revocation behavior. Cover JSON/proxy auth, BaseURL, HTTPS proxy and LAN HTTP explicitly. |
| P0.2 | **Safe file mutation commits.** Define a common confined commit interface, private staging, atomic replacement where supported, and conditional writes using ETags. Add a cross-platform no-replace policy for create/copy/rename. Define partial-directory-copy recovery and interaction with TUS/share invalidation. | Client disconnect, read error, disk-full and competing operations preserve the old destination and a recoverable source. A create-only request cannot overwrite a concurrently created file. An editor cannot silently replace a newer version. Staging content cannot be listed, downloaded, shared, previewed or used as branding. Run on Linux/macOS/Windows plus representative NAS filesystems. Avoid copying entire large NAS files merely to emulate an ordinary same-volume rename. |
| P0.3 | **Effective application CSP.** Bundle editor assets locally, account for Vite legacy scripts/workers, and add per-response nonces or stable hashes. Start with report-only during development, then enforce a tested script policy without unsafe-inline/unsafe-eval. Decide how user content is isolated. | Injected inline scripts and foreign frames fail in browser tests. Login, branding, optional reCAPTCHA, Markdown/KaTeX, editor workers, video, subtitles, PDF and EPUB still work. App HTML and user-content responses each receive the appropriate policy. HSTS stays at the HTTPS endpoint; do not silently impose it on plain LAN deployments. |
| P1.1 | **Sessions UI and API credentials.** List active sessions and revoke one/all; show approximate last activity and transport/device details without treating user-agent/IP as identity. Issue separately scoped, expiring, hashed machine tokens if needed. | Revocation works after restart and for every protected route. No credential material in the session list/logs. API tokens cannot change passwords, create admins or manage sessions without explicit scope. |
| P1.2 | **MFA for local accounts or OIDC integration.** Prefer passkeys/WebAuthn for phishing-resistant local authentication; evaluate TOTP/recovery codes and an OIDC option for existing identity providers. Require recent reauthentication for enrollment, removal and recovery. | Enforce configured origin/RP identity and single-use, expiring challenges; rate-limit attempts. No session before all factors succeed. Test replay, recovery, factor replacement, administrative recovery and revocation of existing sessions. Recovery cannot become an easier account-takeover path. |
| P1.3 | **Per-user resource budgets.** Bound upload size/active TUS jobs, directory/search output, archive bytes/time, thumbnail pixel/memory cost, parallel downloads and disk cache bytes/age. Expose a small set of documented limits. | Predictable 413/429/error responses; bounded memory under many requests; no unlimited waiting queue or orphan cleanup that deletes unrelated files. Test growing files, deep/wide trees, malformed images, cancellation and exhausted storage. Filesystem quotas remain the final disk enforcement boundary. |
| P1.4 | **Proxy-aware abuse controls and audit events.** Resolve client IP only through explicitly trusted proxies; use bounded per-account and per-source failure budgets. Emit structured login/session/admin/share/mutation events with configurable retention. | Forged forwarding headers cannot select an IP or bypass throttling. Several users behind a proxy have a practical rate budget. Logs contain no passwords, bearer tokens, grant cookies or private file contents; quote/escape fields and control path disclosure. |
| P1.5 | **Safer public shares.** New links use at least 128 bits of randomness; add administrator policies for maximum/default expiry and optional mandatory passwords, plus a clear revoke action for share grants. Preserve existing link compatibility. | Expiry arithmetic cannot overflow into unintended long lifetimes. Grant replay after link/password revocation fails. Policy applies server-side to API clients as well as the UI. Existing links can be inventoried and revoked explicitly. |
| P2 | **Continuous assurance and deployment diagnostics.** Fuzz request decoding, path/rule handling, TUS state and share-expiry arithmetic; maintain an authentication/permission test matrix. Add tested backup/restore and diagnostics for proxy transport, permissions and resource limits. | Fuzz cases become small regressions. CI checks release-source identity and dependencies. Backup/restore recovers users, files and settings without exposing the database or backups through the served tree. Diagnostics never print secrets. |

## Next implementation slices

1. **Confined no-replace rename.** Specify backend capabilities before coding. Use native atomic exclusion on supported platforms, preserving anchored parent-directory handles through the operation; do not turn a checked path into an unconstrained syscall. Return an explicit unsupported/conflict error when the filesystem cannot honor the guarantee. Do not emulate exclusion with check-then-rename. Cover concurrent creates, aliases, case-only renames, cross-volume errors and read-only adapters. Preserve fast same-volume renames of large NAS files. Resolve directory source/destination relationships before recursion and add traversal bounds; test copies into descendants through aliases.
2. **Private staging and commit.** Reserve a staging namespace or location with an explicit same-filesystem strategy. A random filename in a served directory is not private: directory shares can expose it. Deny staging across listings, search, raw/download/archive, share, preview, customization/branding and alternate routes before writing sensitive bytes there. Preserve adapter restrictions and define mode/ownership, cleanup after restart, parent-directory durability and quotas. Add fault injection at write, Sync, Close and final commit. Confirm old files survive failure and cleanup never deletes unrelated replacements.
3. **Conditional editor/upload writes and TUS leases.** Build on the commit primitive. Return an ETag at read and enforce `If-Match` at commit, not only before opening. Specify opaque upload IDs, owner/object identity, state expiry and restart behavior, per-user count/size budgets, and cancellation. Bind leases to the namespace across scope aliases/case handling; coordinate rename/delete/copy/editor/ordinary-upload operations. Define inode-reuse behavior and explicitly bound host-side races. Test two accounts with overlapping scopes, renewed sessions, replacement files, partial chunks, aborts and exhausted storage. Keep partial-directory-copy recovery explicit rather than promising a filesystem-wide transaction.
4. **HttpOnly browser authentication as one complete feature.** Define cookie name/path, Secure behavior behind trusted HTTPS proxies and on LAN HTTP, SameSite policy, idle/absolute expiry, and bootstrap/current-user responses. Browser login/renewal must not return a reusable bearer credential to JavaScript. Separate machine credentials from browser cookies; prevent mixed-credential ambiguity. Unsafe requests, including login/logout, need server-side CSRF and origin validation before cookie-authenticated writes are enabled. Handle absent browser metadata and BaseURL explicitly. Clear legacy storage during migration without silently falling back to unsafe bearer handling.
5. **Cross-tab and reauthentication lifecycle.** Specify one renewal owner, completion broadcasts without bearer material, crash/closed-tab recovery and bounded retries. Server-side semantics must tolerate concurrent tabs without turning an invalid old token into authority over a newer session. Logout, password change, sensitive administration and session revocation must converge across tabs and survive restart as intended. Test two tabs, slow/out-of-order responses, lost renewal replies, failed revocation and account switching. Decide whether a lost rotation reply requires re-login or a narrowly bounded recovery protocol; do not leave it implicit.
6. **CSP rollout and content isolation.** Inventory inline bootstrap/legacy code, editor workers, reCAPTCHA and customization. Bundle controllable third-party scripts locally; introduce per-response nonces or stable hashes, then verify report-only results in a disposable fixture before enforcement. Define policy for user HTML/SVG and media/PDF/EPUB; consider a separate content origin where feasible. Test injection blocking and legitimate rendering. Report collection must not become an unbounded or secret-bearing log sink.

P1 can then add session management, scoped machine credentials, passkeys/MFA, resource budgets and auditable administrative actions. For shares, ship server-enforced lifetime/password policy with inventory/migration behavior together; increasing new-link entropy alone does not upgrade old links.

## Acceptance and publication gates

- Each security repair needs a small failing reproduction and successful authorized-path coverage. Maintain the permission matrix for anonymous, Create-only, Modify, Delete, Download, Share and administrator roles; include overlapping scopes and revoked/renewed sessions.
- Run Go vet/race tests and frontend lint/tests/typecheck/build. Test native Linux and Windows behavior before claiming platform coverage; cross-compilation alone is insufficient. Test relevant operations on the intended NAS filesystem with disposable data before a later rollout. Recheck dependency advisories without broadening exceptions.
- Give each slice a compatibility note and mark implementation status accurately. No raw credentials in diagnostics, fixtures or audit events. No production data in regression tests.
- When publishing is authorized later, verify immutable source/image identity, both supported container architectures, copied-database migration and backup restoration. A local green build does not change the running NAS. This plan does not schedule or authorize publication.

The session, CSRF, CSP and MFA controls are informed by primary [OWASP session guidance](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html), [CSRF guidance](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html), [CSP guidance](https://cheatsheetseries.owasp.org/cheatsheets/Content_Security_Policy_Cheat_Sheet.html) and [MFA guidance](https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html), checked on 2026-10-21. The sequencing, implementation slices and acceptance gates are project-specific design proposals.
